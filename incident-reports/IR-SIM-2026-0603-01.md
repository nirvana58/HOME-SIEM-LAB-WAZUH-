# Incident Report: Credential-Harvesting Phishing Page (Instagram Lookalike)

> **Classification:** Simulated incident · Isolated lab environment  
> **Incident ID:** IR-SIM-2026-0603-01 · **Version:** 1.0 · **Status:** Final  
> **Activity date:** 3 June 2026 · **Analyst:** Lakshmeesha Suvarna  
> **Handling:** TLP:CLEAR. Public IP address and tunnel hostname are redacted.

## 1. Executive summary

On 3 June 2026, a controlled lab simulation reproduced a credential-harvesting phishing flow. A workstation opened a hand-built page imitating Instagram's login screen, exposed through an ngrok tunnel. Approximately 95 seconds after the page loaded, the user submitted a username/password pair. JavaScript sent the values in a JSON request to `POST /api/submit`; the backend stored the test data and returned a success response. The page then displayed “Login successful!” without redirecting to Instagram.

All submitted values were dummy test strings. No real users, accounts, or credentials were involved. The page, tunnel, and workstation were controlled by the analyst.

**Severity in a production environment: High.** A real credential pair could enable account takeover or credential reuse against corporate single sign-on. The lab itself is informational because only dummy data was used.

### Key findings

- The page imitated Instagram with branded styling, login text, social-login and account-creation buttons, and a Meta footer.
- A page script intercepted form submission and sent values to a relative endpoint, `/api/submit`, using generic JSON keys `field_one` and `field_two`.
- The observed backend chain included ngrok, Apache, FastAPI/Uvicorn, and Supabase.
- The browser accepted the ngrok free-tier warning page; the `abuse_interstitial` cookie was present.
- The packet capture was taken behind the tunnel and Apache reverse proxy, after TLS termination. Therefore, it exposed the request body in this lab, but does **not** represent what an ordinary network sensor on the victim side would see.

## 2. Scope and assumptions

- **Authorization:** The analyst built and operated the page, tunnel, and victim workstation. No third-party systems or people were targeted.
- **Delivery vector:** Not recorded. ATT&CK mapping assumes a link was delivered, but the actual delivery method cannot be established from this evidence.
- **Lab topology:** The victim browser and attacker-hosted page were on the same workstation. The public IP shown in forwarding headers and the tunnel hostname therefore refer to the lab's shared public address; this should not be interpreted as evidence of attacker/victim identity in a real incident.
- **Timestamp handling:** The first capture timestamp belongs to `GET /`, not the credential POST. The POST time is derived from packet-relative timing and cross-checked against the HTTP response Date header.

**Important visibility limitation:** Between a real victim and the tunnel provider, the connection would use HTTPS. This capture could read the POST body because it was collected on the server side of TLS termination. A corporate SOC would usually rely on DNS, TLS server-name information where available, destination reputation, byte/connection patterns, endpoint telemetry, and proxy logs—not the credential values themselves.

## 4. Technical analysis

### 4.1 Page behavior

- **Brand impersonation:** The page title was “Instagram”; the heading read “Log into Instagram”. It used Instagram-style gradient branding, “Log in with Facebook” and “Create new account” buttons, and a “© 2026 Instagram from Meta” footer.
- **Resource loading:** The logo was an inline vector graphic. Google Fonts (Grand Hotel and DM Sans) were the only noted third-party resources; the initial notes' claim that Instagram logos were loaded from a CDN was incorrect.
- **Credential capture:** On submit, JavaScript cancelled normal form navigation, read the two input values, and sent them as JSON to `/api/submit`. Generic field names obscured the meaning of the values.
- **User feedback:** The page displayed “Login successful!” and cleared the form, but never redirected to the real service. This was a potential warning sign for a careful user.
- **Infrastructure clue:** A developer comment described the ngrok → Apache → FastAPI → Supabase chain.
- **Template artefacts:** Requests to `/_vercel/insights/script.js` and `/_vercel/speed-insights/script.js` returned 404 responses, consistent with leftover code from a Vercel project.
- **Implementation defect:** The password-visibility toggle referenced an element named `password` rather than the observed `input2`, so the control would fail.

Observed request characteristics included `Content-Type: application/json`, Origin and Referer values pointing to the tunnel hostname, script-initiated Fetch metadata, forwarding headers, `X-Forwarded-Proto: https`, and a `uvicorn` server banner. The browser user agent identified Brave on Chromium 148 running Windows; that user-agent string does not reliably distinguish Windows 10 from Windows 11.

The cookie `abuse_interstitial=<hostname>` indicated that the browser had passed through ngrok's free-tier warning page.

### 4.3 Submitted data

The POST body contained two short dummy test strings under `field_one` and `field_two`. No real credentials were submitted. In a production incident, a confirmed pair of working credentials should be treated as compromised.

## 9. Detection, containment, and response

### 9.1 Production detection opportunities

- DNS queries or TLS server-name telemetry for tunnelling-service domains, especially hosts not previously seen in the organisation.
- Secure web gateway or proxy logs showing a login-style page hosted on a new or uncategorized domain.
- Browser/EDR telemetry indicating credential-like submissions to low-reputation destinations.
- User reports submitted through a report-phishing control.
- Threat-intelligence and URL-scanning verdicts, with exact scanned URL and timestamp preserved.

Because the available PCAP was captured behind TLS termination, a production network sensor should not be expected to see the submitted credential values.

### 9.2 Recommended response actions

| Priority | Action | Lab status |
|---|---|---|
| 1 | Establish which account was entered and whether it was a corporate identity | Not applicable; dummy data only |
| 1 | For a real affected account, reset the password, revoke sessions/tokens, review MFA methods, and inspect sign-in logs | Recommended for production |
| 1 | Block the confirmed malicious FQDN/URL at DNS and web proxy, using care with shared hosting services | Recommended for production |
| 2 | If delivered by email/chat, locate and remove copies and identify recipients | Delivery vector not recorded |
| 2 | Search for other hosts that resolved or visited the same hostname | Recommended |
| 2 | Review account sign-in activity after the submission time | Recommended |
| 3 | Report the page to the tunnel provider and impersonated brand; submit the URL to browser safe-browsing services | Recommended |
| 3 | Notify affected users and provide targeted awareness guidance | Recommended |

## 10. Root cause and contributing factors

**Root cause:** Interaction with a convincing lookalike login page in the controlled simulation.

Contributing factors observed or identified in the scenario:

- The user clicked through the tunnelling service's warning page.
- In a production environment, a password alone may be sufficient if phishing-resistant MFA is absent.
- The lab did not have a control that alerted on tunnelling-service domains.
- The fake page provided no obvious clue beyond failing to redirect to the real service.

## 11. Recommendations

| Priority | Recommendation |
|---|---|
| High | Deploy phishing-resistant MFA, such as passkeys or FIDO2 security keys, for corporate accounts |
| High | Alert on DNS/proxy activity to tunnelling services, with an allow-list for approved development use |
| High | Use a managed password manager with domain-bound autofill to reduce credential entry on lookalike domains |
| Medium | Develop and test Sigma/Wazuh detections for new tunnel hostnames, suspicious POST activity to unknown hosts, and relevant page-content signals |
| Medium | Enable endpoint DNS logging (for example, Sysmon Event ID 22 where applicable) and forward useful browser/EDR telemetry |
| Medium | Provide a one-click phishing-reporting option and a short response playbook for lookalike-login incidents |
| Low | Run periodic phishing simulations and measure reporting rates as well as click rates |

## 12. Lessons learned

1. **Capture point determines what can be claimed.** A capture behind a tunnel proves the backend mechanics but overstates what a victim-side SOC sensor would observe.
2. **Prioritize behavioral and infrastructure signals.** Tunnel domains, unusual request paths, page content, reputation, and missing expected redirects are more useful than captured credential values.
3. **Make timestamps reproducible.** Use UTC, identify the packet/request associated with each time, and cross-check derived timestamps.
4. **Separate observation from inference.** Clearly label assumptions, likely template artefacts, approximate ATT&CK mappings, and findings from a separately hosted copy.
5. **Do not over-trust individual detection engines.** Correlate reputation feeds, content analysis, telemetry, and ML outputs.
